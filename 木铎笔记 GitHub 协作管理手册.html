2. 协作原则

main 只放稳定版本 组长负责整合本组代码 组员只推送到自己的个人分支 窦思颖审核组长分支 合并必须走 Pull Request

角色可以直接 push 到哪里应该向哪里发 Pull Request不建议做什么
普通组员 自己的个人分支，例如 g1-zym 本组组长整合分支，例如 leader-g1-mty 不要直接 push 到 main；不要直接合并到其他小组分支。
小组组长 自己的组长整合分支，例如 leader-g1-mty main 不要绕过 PR 直接改 main。
总负责人窦思颖 main，以及必要时维护各组长分支 通常不需要向别人发 PR 不要在没有审核 Files changed 的情况下合并。
所有成员必须自觉遵守： 不要直接 push 到 main； 提交后必须在 GitHub 上创建 Pull Request； 没有 PR 的提交不会被视为正式提交。

4. 重要：git push 和 Pull Request 不是一回事

结论：git push 只表示“把本地提交上传到 GitHub 的某个分支”。它不会自动创建 Pull Request，也不会自动合并到目标分支。
操作在哪里做作用是否会让 PR 页面出现记录
git push 本地终端 / VS Code 终端 把本地分支提交上传到 GitHub 对应分支 不会自动创建 PR。最多 GitHub 首页出现 “recent pushes” 提醒。
Create pull request GitHub 网站 Pull requests 页面 正式发起“把某分支合并到目标分支”的审核请求 会。PR 页面会出现一条 Open Pull Request。
Merge pull request GitHub 网站 PR 页面 审核通过后，把 compare 分支合并到 base 分支 会。PR 变成 Merged / Closed。

如果有人说“我已经提交了”，需要追问两件事

  1. 你是否已经执行了 git push？如果没有，代码还只在你自己电脑上。
  2. 你是否已经在 GitHub 网站创建了 Pull Request？如果没有，负责人或组长在 PR 页面看不到审核请求。

正确提交链路

本地修改代码
  ↓
git add .
  ↓
git commit -m "说明"
  ↓
git push
  ↓
打开 GitHub 网站
  ↓
Compare & pull request
  ↓
确认 base 和 compare
  ↓
Create pull request
  ↓
等待组长 / 总负责人审核

5.2 每次审核前

先更新本地对 GitHub 的认知。

git checkout main
git pull origin main
git fetch origin
git status

理想状态：

On branch main
Your branch is up to date with 'origin/main'.
nothing to commit, working tree clean
5.3 本地预审组长分支

以小组1组长分支为例，查看它相对 main 多了哪些提交、改了哪些文件。

# 看 leader-g1-mty 比 main 多了哪些提交
git log --oneline origin/main..origin/leader-g1-mty

# 看改了哪些文件
git diff --name-status origin/main..origin/leader-g1-mty

# 看具体改动
git diff origin/main..origin/leader-g1-mty

审核小组2或小组3时，把分支名换成：

origin/leader-g2-lyx
origin/leader-g3-mty
5.4 GitHub 上审核并合并
  1. 打开 GitHub 仓库 → Pull requests。
  2. 打开组长提交的 PR。
  3. 确认方向正确： 
    base: main
compare: leader-g1-mty / leader-g2-lyx / leader-g3-mty
  4. 点击 Files changed 审核具体代码。
  5. 确认无问题后点击 Merge pull request。
  6. 合并后同步本地 main。
git checkout main
git pull origin main
组长分支是长期整合分支，合并后通常不要删除 leader-g1-mty、leader-g2-lyx、leader-g3-mty。

6. 各小组组长操作流程

6.1 组长分支对应关系

组长管理小组组长整合分支接收哪些成员 PR
马天一 小组1 leader-g1-mty g1-mty、g1-zym、g1-lyj
李益行 小组2 leader-g2-lyx g2-lyx、g2-shm、g2-zjx
马天一 小组3 leader-g3-mty g3-mty、g3-rsr、g3-wcy、g3-lyt、g3-lzy
6.2 组长每天开始前

以小组1马天一为例：

git fetch origin
git checkout leader-g1-mty
git merge origin/main
git push

这一步的意思是：先让组长整合分支吸收最新 main，后续合并组员代码时更不容易冲突。

6.3 组长审核组员 PR

组员在 GitHub 上创建 PR，例如：

base: leader-g1-mty
compare: g1-zym

组长需要在 GitHub 的 PR 页面：

  1. 确认 PR 方向是不是合到本组组长分支。
  2. 点击 Files changed 看改动。
  3. 确认没有敏感文件、无关文件和明显错误。
  4. 点击 Merge pull request。
6.4 组长提交给总负责人

当本组阶段性任务完成后，组长在 GitHub 上创建 PR 给总负责人审核。

小组1：
base: main
compare: leader-g1-mty

小组2：
base: main
compare: leader-g2-lyx

小组3：
base: main
compare: leader-g3-mty

PR 描述建议写清楚：

  • 本组完成了哪些任务；
  • 涉及哪些前端/后端/文档模块；
  • 是否需要安装新依赖；
  • 是否已经本地运行或自测。

6.5 马天一同时管理两个小组时的注意事项

马天一需要特别注意当前分支，避免把小组1代码提交到小组3分支，或者把小组3代码提交到小组1分支。 
# 做小组1相关工作前
git checkout leader-g1-mty
git status

# 做小组3相关工作前
git checkout leader-g3-mty
git status

8. 命令详解：什么时候用、什么意思、预期输出

场景命令含义预期输出 / 判断标准
查看当前状态 git status 看当前在哪个分支，有没有未提交改动 On branch g1-zym；理想是 nothing to commit, working tree clean
查看本地分支 git branch 列出本地分支 带 * 的是当前分支，例如 * g1-zym
查看远程分支 git branch -r 列出 GitHub 上的远程分支快照 origin/main、origin/leader-g1-mty、origin/g1-zym
更新远程信息 git fetch origin 只更新远程分支信息，不会改当前代码文件 可能显示 [new branch] 或 main -> origin/main
切换分支 git checkout g1-zym 切换到本地已有分支 Switched to branch 'g1-zym'
远程有分支但本地没有 git checkout -b g1-zym origin/g1-zym 在本地创建并切换到该分支，同时跟踪远程分支 Switched to a new branch 'g1-zym'
同步 main git pull origin main 当前在 main 时，把 GitHub 最新 main 拉到本地 main Already up to date. 或 Updating ...
组员同步组长分支 git merge origin/leader-g1-mty 当前在个人分支时，把组长分支最新内容合进来 Already up to date. 或 Merge made by the 'ort' strategy.
组长同步 main git merge origin/main 当前在组长分支时，把 main 最新内容合进来 如进入 Vim，按 Esc，输入 :wq 回车
查看具体改动 git diff 看当前还没提交的改动 + 是新增，- 是删除
加入暂存区 git add . 把当前目录下所有改动准备加入下一次提交 通常没有输出
提交到本地 git commit -m "说明" 生成一个本地提交 [g1-zym abc1234] 说明
推送到远程 git push 把本地提交上传到 GitHub 对应分支 Enumerating objects...、Writing objects...
第一次推送新分支 git push -u origin g1-zym 推送并建立本地分支与远程分支的跟踪关系 branch 'g1-zym' set up to track...
负责人查看组长分支提交 git log --oneline origin/main..origin/leader-g1-mty 看小组1组长分支比 main 多了哪些提交 显示短 commit id 和提交信息
负责人查看组长分支文件变化 git diff --name-status origin/main..origin/leader-g1-mty 只看变更文件列表 M 修改，A 新增，D 删除
负责人查看具体代码差异 git diff origin/main..origin/leader-g1-mty 查看组长分支相对 main 的完整差异 + 新增行，- 删除行

9. 审核清单

9.1 组长审核组员 PR

  • ✅ PR 方向正确：base 是本组组长分支，compare 是组员个人分支。
  • ✅ 改动内容属于该组员负责的任务。
  • ✅ 没有误提交 .venv/、node_modules/、*.sqlite3、.env。
  • ✅ 没有真实账号、密码、token、隐私信息。
  • ✅ 依赖文件改动合理，例如 package-lock.json、requirements.txt。
  • ✅ 没有大面积删除无关文件。

9.2 总负责人审核组长 PR

  • ✅ PR 方向正确：base: main，compare: leader-g1-mty / leader-g2-lyx / leader-g3-mty。
  • ✅ 组长已经整合并审核本组成员提交。
  • ✅ Files changed 中无敏感文件、环境文件、数据库文件。
  • ✅ 代码改动范围与本阶段任务一致。
  • ✅ 如涉及前后端联调，PR 描述中说明接口、页面和测试情况。
  • ✅ GitHub 显示可合并，或者冲突已经解决。

10. 常见问题

问题 1：为什么我 push 了，但 Pull Request 页面没有东西？

因为 git push 只上传分支，不会自动创建 PR。需要打开 GitHub 网站，点击 Compare & pull request 或进入 Pull requests → New pull request 手动创建。

问题 2：切换分支时报错 pathspec did not match

说明本地没有这个分支。先获取远程分支列表，再创建本地跟踪分支。

git fetch origin
git branch -r
git checkout -b g1-zym origin/g1-zym

问题 3：merge 后进入 Vim，不知道怎么办

这是 Git 让你确认合并提交信息。默认信息可以保留。

按 Esc
输入 :wq
回车

问题 4：误提交了虚拟环境、数据库或密钥文件

先加入 .gitignore，再从 Git 跟踪中移除。

# .gitignore 建议包含：
.venv/
backend/.venv/
node_modules/
*.sqlite3
.env
__pycache__/
*.pyc
*.egg-info/

# 如果已经被 Git 跟踪：
git rm -r --cached backend/.venv
git rm --cached backend/muduo_dev.sqlite3
git add .gitignore
git commit -m "忽略本地环境和数据库文件"
git push

问题 5：当前分支 ahead by N commits

表示本地有提交还没有推送到 GitHub。确认无误后：

git push

问题 6：当前分支 behind by N commits

表示 GitHub 上该分支有新提交，本地还没有。通常先 fetch，再 merge。

git fetch origin
git merge origin/当前分支名

问题 7：合并冲突

Git 会在冲突文件里留下标记：

<<<<<<< HEAD
你当前分支的内容
=======
对方分支的内容
>>>>>>> origin/xxx

处理方法：

手动编辑文件，保留正确内容，删除冲突标记
git add 冲突文件
git commit
git push

问题 8：马天一两个分支混淆怎么办？

每次操作前先看当前分支。

git branch
git status

如果是小组1任务，应该在 g1-mty 或 leader-g1-mty；如果是小组3任务，应该在 g3-mty 或 leader-g3-mty。

一句话总流程

普通组员：
自己的分支开发 → git push → GitHub 创建 PR 到本组组长分支 → 等组长审核

小组组长：
审核本组成员 PR → 合并到组长整合分支 → 阶段完成后创建 PR 到 main → 等窦思颖审核

总负责人窦思颖：
审核各组长分支 PR → 确认安全和功能正确 → Merge pull request 到 main
